**结论先行。** 这不是"48 GB 不够用"，而是三件事叠加：

1. 被杀的 51 个进程 oom_score_adj 全部约为 +800，所以 earlyoom 每次都选中 45 MB 的 git，而不是真正吃内存的进程。这是配置反模式，也是"连杀 51 个却止不住"的直接原因。
2. herdweb 收到 SIGTERM 后走优雅退出、返回 0，而 unit 是 `Restart=on-failure`，systemd 视为正常停止，不重启。502 持续到你手动 update-prod，原因在这里，与隧道无关。
3. 谁在 08:39 到 08:50 之间把内存吃穿，现有证据定不了位。`memory.peak` 数据不能证明你的假设 1，理由见下。

## 证据解读的纠错

- **badness 802 配 VmRSS 45 MiB 只有一种解释。** 内核 oom_score 约等于 oom_score_adj 加上 RSS 占总量的千分比。45 MiB 占 52 GB 不到 1 点，剩下的 800 只能来自 oom_score_adj。hermes、uvicorn、herdweb 的主 PID、python3、ps 也都是 800 出头，同一来源。未被杀的 pi/claude 会话如果也是 +800，一个 7 GB 会话会到 930 以上、必先被选中，所以它们的 adj 更低。这是一次"基础服务当替罪羊、真凶免死"的倒挂。
- **38 个 git 不是并发，是连环。** 每次 earlyoom 杀掉一个 git，agent 重试命令又拉起一个新的 +800 的 git，它立刻成为全机最高分。earlyoom 在 10 分钟里循环杀 45 MB 的进程，释放量约等于零，压力源一直在。08:43 内核 OOM 仍然发生，证明这些击杀没有起效。
- **earlyoom 的触发是 AND，不是"swap 一满就杀"。** 它要求 mem avail 和 swap free 同时低于阈值。4 GB swap 在压力下总是先满，于是 swap 条件形同虚设，实际阈值退化成"可用内存低于 4.8 GB"。swappiness=10 不是原因，缓存耗尽后内核照样换页。
- **`memory.peak` 包含 page cache 和全部子进程。** cgroup v2 的计数把文件缓存也记在 cgroup 上。一个 run-*.scope 里跑过 `pnpm test`、tsc、esbuild、git 读大仓库，就会攒出好几 GB 缓存，而缓存在压力下会被回收。所以"每个会话峰值 5 到 7 GB"不能读成"CLI 堆 5 到 7 GB"，现在的 0.25 到 1.2 GB 才是常驻。
- **不同时刻的峰值不能相加。** app.slice 40.66 GB 与 claude.slice 32 GB 峰值时间相差 12 分钟、总和超过物理内存，说明它们不是同时发生。按你贴的时间，今天抬升峰值的是 session-30.scope、ai-usage-monitor（08:43:10，内核 OOM 前 11 秒到 7 GB）和 session-187.scope，claude.slice 下没有一个 run-*.scope 今天创新高。这与假设 1 相反。
- **"峰值最后抬升于"这个时间戳来源需要核实。** 如果它是 cgroupfs 文件的 mtime，那不可信：kernfs 不会在内核内部更新计数值时刷新 mtime，你看到的多半是 inode 被实例化的时间。验证方法：连续两次 `stat` 同一个 memory.peak，中间让该 cgroup 分配一大块内存，看 mtime 是否变化。
- **"被杀的 herdweb 只有 73 MiB"是包装进程。** ExecMainPID 是 serve-prod.sh exec 出来的 pnpm，真正的 Node 服务是它的子进程（日志里打 "shutting down" 的 1348174），RSS 未知。
- **内核选中一个 anon-rss 只有 2.4 MB 的 pi。** 这说明那个 pi 的堆几乎全在 swap 里（内核 badness 计入 swapents）。杀它释放的是 swap 不是 RAM，所以挤压一直持续到 08:50。这也暗示 4 GB swap 里塞的是闲置 agent 会话的堆。

## 五个问题

**1. 机制。** earlyoom 按设计工作，但被 +800 的 adj 引偏了方向，这是反模式。先找 800 从哪来：

```bash
# 按 adj 值和 cgroup 聚合全部 uid 1000 进程
for p in /proc/[0-9]*; do
  [ "$(stat -c %u $p)" = 1000 ] || continue
  echo "$(cat $p/oom_score_adj) $(cut -d: -f3 $p/cgroup | head -1) $(cat $p/comm)"
done 2>/dev/null | sort | uniq -c | sort -rn | head -30
cat /proc/$(pgrep -u 1000 -o -x systemd)/oom_score_adj     # 用户 manager 本身
systemctl show user@1000.service -p OOMScoreAdjust
grep -rn OOMScoreAdjust ~/.config/systemd/ /etc/systemd/user.conf /etc/systemd/system/user@.service.d/ 2>/dev/null
```

我最怀疑 `user@1000.service` 或用户 manager 被设成了 800，于是所有用户 unit 继承 800 且无法降低，而从 SSH 登录 shell 启动的 agent 会话保持 0。

**2. 主犯。** 假设 1 不成立，至少证据不支持。更硬的取证路径是进程级时序而不是 cgroup 高水位，事后只能靠内核任务表。任务表缺失的排查顺序：

```bash
sysctl vm.oom_dump_tasks                    # 应为 1
dmesg -T | grep -c 'Tasks state'            # ring buffer 是否还在
journalctl -b -u systemd-journald | grep -i 'missed.*kernel'   # journald 漏读 kmsg
ls /var/log/kern.log* /var/log/syslog* 2>/dev/null
journalctl -k -b -o short-iso | grep -B3 -A80 'oom-kill' | head -120
```

任务表有上千行，一次打印就是一个 printk 突发，journald 漏读 kmsg 时会记 "Missed N kernel messages"，这是最常见的原因。当前最可疑的单点是 ai-usage-monitor：一个监控服务不该到 7 GB，且它的峰值紧贴内核 OOM。查它现在的 `memory.current`、`memory.stat` 里的 anon 值、它扫描的目录大小，以及 journal 里它在 08:39 前后是否有一次运行。

**3. 5 到 7 GB 是否异常。** 以我的经验，agent CLI 单进程堆常驻 0.5 到 2 GB 属正常，长上下文会到 3 GB 上下。scope 峰值 5 到 7 GB 不异常，因为它包含测试、构建、MCP 子进程和缓存。最省事的定位是先分清 anon 与 file，再分清哪个 PID：

```bash
for s in /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/claude.slice/run-*.scope; do
  printf '%s anon=%s file=%s\n' "$(basename $s)" \
    "$(awk '/^anon /{print $2}' $s/memory.stat)" "$(awk '/^file /{print $2}' $s/memory.stat)"
done
ps -eo pid,ppid,rss,comm,args --sort=-rss | awk '$3>300000' | head -30
```

如果要证明是 V8 堆，用 `NODE_OPTIONS=--max-old-space-size=2048` 起一个会话，撞到就报 heap out of memory，没撞到说明增长在堆外。前提是 CLI 是普通 Node 脚本；若是打包的单文件可执行，NODE_OPTIONS 可能被忽略，这一点我无法从仓库确认。heap snapshot 不推荐，几 GB 的堆做快照本身就会把机器推进 OOM。

**4. 止血与根治。** 按性价比排序：

| 序 | 方案 | 作用 | 副作用与风险 |
| --- | --- | --- | --- |
| 1 | 修正 oom_score_adj 倒挂：找到 800 的来源并去掉；agent 所在 slice 设高值 | 让内核和 earlyoom 都先杀吃内存的会话 | 用户 manager 若已是 800，用户 unit 无权往下调，必须在系统级 user@.service 的 drop-in 改 |
| 2 | herdweb.service 改 `Restart=always`，加 `StartLimitIntervalSec=60`、`StartLimitBurst=5` | 被杀后 3 秒自动回来，502 缩短到秒级 | 服务真坏时会循环重启，被 StartLimit 兜住 |
| 3 | 给 claude.slice 和 session scope 所在层级设 `MemoryHigh`，ai-usage-monitor 设 `MemoryMax=2G` | 增长被限制在自己的 cgroup 里，内核在 cgroup 内部选最大的会话杀 | MemoryHigh 超过后会话会被节流变慢；MemoryMax 触发 cgroup 内 OOM |
| 4 | 启用 systemd-oomd，在 claude.slice 上设 `ManagedOOMMemoryPressure=kill` | 按压力整体杀掉最重的那个会话 cgroup，而不是零碎 git | 与 earlyoom 并存是双杀手，需把 earlyoom 阈值降到 `-m 5 -s 2` 或停用 |
| 5 | 加 zram 8 到 16 GB，swappiness 提到 100 以上，earlyoom 阈值随之调整 | 闲置会话的堆压缩存放，swap 不再秒满 | 压缩占 CPU；zram 本身占内存；与磁盘 swap 要设优先级 |
| 6 | earlyoom 加 `--avoid '^(herdweb|cloudflared|sshd|tmux|herdr)$'` 和 `--prefer '^(pi|claude|node)$'` | 只影响 earlyoom 的选人 | 对内核 OOM 无效；prefer 只加 300 分，压不过 800 的倒挂 |
| 7 | 退出跑完的 agent 会话，限制并发数 | 直接减少常驻 | 靠纪律，不可靠 |

"不做就还会再发生"的是第 3 条加第 4 条：在 agent 所在 cgroup 上设上限并让压力杀落在那个 cgroup。第 1 条只改变谁死，第 2 条只缩短 502，第 5 条只是推迟。

**5. 复发取证保底。** 最小方案是三层：

- **常驻采样。** 装 `atop`，采样间隔 30 秒，它按进程记录 RSS 和 swap 历史。内存约 20 MB，磁盘每天约 100 到 200 MB，日志默认 28 天轮转，可在 `/etc/default/atop` 缩短。不想装包就用 systemd timer 每 30 秒执行以下脚本，落盘到 `/var/log/memwatch/`，每天一个文件，每天约 15 MB：

```bash
#!/usr/bin/env bash
d=/var/log/memwatch; mkdir -p $d; f=$d/$(date +%F).log
{ date -Is; grep -E 'MemAvailable|SwapFree' /proc/meminfo; cat /proc/pressure/memory
  ps -eo pid,rss,oom_score,comm,args --sort=-rss | head -25 | cut -c1-160
  for s in /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/{claude.slice/run-*.scope,app.slice/*.service}; do
    printf '%s cur=%s anon=%s\n' "${s##*/}" "$(cat $s/memory.current)" "$(awk '/^anon /{print $2}' $s/memory.stat)"
  done 2>/dev/null; echo; } >> $f
```

- **击杀瞬间快照。** earlyoom 支持 `-N /usr/local/bin/oom-hook.sh`，每次击杀后调用，环境变量给 `EARLYOOM_PID`、`EARLYOOM_NAME`。让它执行上面同一段采样脚本，落到 `/var/log/memwatch/kill-<时间>.log`。这样下次第一刀落下时，前 25 名 RSS 已经在盘上。
- **内核侧保证。** `sysctl vm.oom_dump_tasks=1`，journald 里设 `RateLimitIntervalSec=0` 只对 journald 自身单元没用，关键是确认没有 "Missed kernel messages"；同时把 `dmesg` 环缓冲加大：内核参数 `log_buf_len=8M`。

一个未知项要补：agent 会话到底以什么 adj 运行、由谁启动到 claude.slice，仓库里没有这部分（`systemd-run` 或 herd 启动器不在本仓）。上面第 1 条的聚合命令跑完，主犯和倒挂来源会一起浮出来。
